# 右键菜单定位问题 · 交接文档

> **2026-11-17 状态：本机修复版菜单回归已通过。** 先看下方的最终结论；后续旧章节保留排查历史，其中有关 WindowChrome、AbsolutePoint 和默认编辑菜单的推测不能当作已验证事实。

## 本次修复与验证

**结论**：原因是本机 Windows 的 MenuDropAlignment（菜单右边缘对齐）为 1。WPF 会把一级、二级、三级菜单优先放到左侧。它是系统菜单方向设置导致的正常框架行为，和本产品要求的“空间足够时向右展开”不一致。

普通窗口、自定义边框窗口及透明窗口均已做对照，排除了 WindowChrome 是此问题根因的旧推测。单独给二级菜单设置 Placement=Right 仍不能绕过系统对齐设置；打开后强制移动菜单窗口的旧方案也不能统一覆盖默认编辑菜单和多级菜单。

**实施**：在 App.xaml.cs 启动时，先读 SystemParameters.MenuDropAlignment 初始化缓存，再把已核实的私有布尔缓存 _menuDropAlignment 设为 false。系统通知重新读取缓存后同步应用。只影响外壳进程，屏幕右侧放不下时仍由 WPF 自动向左避让。

移除了原来的菜单 SetWindowPos 搬动逻辑、全局菜单钩子和 App.xaml 的禁用编辑菜单样式。各页面现有的 MenuOpened 转发只记录日志。默认编辑菜单会在右键或菜单键触发时临时创建；编辑框的 ContextMenu 属性为 null 不能证明它被禁用了。

**回归结果**：

| 模式 | 通过 | 失败 | Windows 原始对齐值 |
|---|---:|---:|---:|
| 跳过修复，重现问题 | 61 | 45 | 1 |
| 应用修复 | 106 | 0 | 1 |

覆盖主副屏（含负坐标）、普通/自定义边框/透明窗口、菜单重复打开、一至三级方向、键盘打开子菜单、真实菜单 Click（点击事件）、设置/搜索/详情样式的临时编辑菜单和命令路由、屏幕右边缘自动避让。两次额外调用 WPF 的 SystemParameters.InvalidateCache(int) 菜单缓存失效路径，确认系统通知处理器会同步重新应用修复，没有手动重跑初始化来掩盖问题，也未调用 Windows 参数设置接口。测试只创建一次性窗口；不连接数据库，编辑菜单的测试命令在执行前被拦截，不改变系统剪贴板。

## 一、问题现象

所有 `ContextMenu`（右键菜单）**出现在鼠标左下方，而不是右下**。

### 用户实测记录

| 位置 | 现象 |
|---|---|
| 主界面条目右键 | ✅ 正确（右下） |
| 主界面左侧分组区右键 | ❌ 左下 |
| 快捷面板条目右键 | ❌ 左下 |
| 条目详情内容右键 | ❌ 左下 + **菜单无法点击** |
| 设置页任何地方右键 | ❌ 左下 |
| 整理窗口右键 | ❌ 左下 |
| 二级菜单（组 → 移到分组） | ❌ 在父菜单**左侧**展开 |

### 精确几何关系（用户截图实测）

```
鼠标位置：约 (477, 225)
菜单范围：x = 190 ~ 465
菜单宽度：275px

190 + 275 = 465  ← 菜单右边缘
477 - 465 = 12   ← 鼠标到菜单右边缘的距离
```

**菜单右边缘对齐到鼠标位置**（而不是左边缘）。这是 `PlacementMode.MousePoint` 在某些情况下的实际行为。

## 三、已尝试方案与结果（7 次，全部失败或部分失败）

### 尝试 1：`PlacementMode.AbsolutePoint` + 屏幕坐标

```csharp
GetCursorPos(out var p);   // 屏幕物理像素
menu.Placement = PlacementMode.AbsolutePoint;
menu.HorizontalOffset = p.X;
menu.VerticalOffset = p.Y;
```

**失败**。`AbsolutePoint` 的 `HorizontalOffset` 是**相对于 `PlacementTarget`**，不是屏幕绝对坐标。

### 尝试 2：删除 `PlacementRectangle="0,0,0,0"`

**部分改善**。这个属性把菜单锚定到元素的左上角。

**注意**：项目里曾同时存在 `Placement="MousePoint"` 和 `PlacementRectangle="0,0,0,0"`，两者叠加是「菜单在元素左上角」的直接原因。

### 尝试 3：P/Invoke `GetCursorPos`（自定义方法名，无 EntryPoint）

```csharp
[DllImport("user32.dll")]
private static extern bool GetCursorPosRaw(out POINT lpPoint);
```

**完全失败**，日志证据：

```
ERROR Unable to find an entry point named 'GetCursorPosRaw' in DLL 'user32.dll'.
```

P/Invoke 默认用**方法名**当 DLL 入口名。`user32.dll` 里只有 `GetCursorPos`。

**修法**（已应用）：

```csharp
[DllImport("user32.dll", EntryPoint = "GetCursorPos")]
```

### 尝试 4：P/Invoke `SetWindowPos`（同样的 EntryPoint 错误）

```
ERROR Unable to find an entry point named 'SetWindowPosGlobal' in DLL 'user32.dll'.
```

**同一个错误犯了两次。** 已修：`EntryPoint = "SetWindowPos"`。

### 尝试 5：`App.xaml` 隐式 Style + `EventSetter`

```xml
<Style TargetType="{x:Type ContextMenu}">
  <EventSetter Event="Opened" Handler="OnAnyMenuOpened"/>
</Style>
```

**完全失败**。日志里**没有任何 `[hook]` 或 `Opened` 记录**，说明 `EventSetter` 在隐式 Style 里对 `ContextMenu` 不生效。

### 尝试 6：`EventManager.RegisterClassHandler`

```csharp
EventManager.RegisterClassHandler(
    typeof(FrameworkElement),
    ContextMenuService.ContextMenuOpeningEvent,
    new ContextMenuEventHandler(OnAnyContextMenuOpening));
```

**完全失败**。日志里只有 18 次重复的 `global cursor=(1272,985)`（隧道事件在每层祖先都触发），但**菜单位置没变**。

同样尝试了：

```csharp
EventManager.RegisterClassHandler(
    typeof(ContextMenu),
    FrameworkElement.LoadedEvent,
    new RoutedEventHandler(...));
```

**也失败**。`ContextMenu` 的 `Loaded` 不通过类处理器触发（因为它是 Popup 内容，不在标准视觉树里）。

### 尝试 7：每个 `ContextMenu` 显式挂 `Opened="Menu_Opened"`

**这是目前唯一部分成功的方案。**

XAML：

```xml
<ContextMenu Placement="MousePoint" MaxWidth="280" Opened="Menu_Opened">
```

code-behind（`MainWindowView.xaml.cs` / `QuickPanelView.xaml.cs`）：

```csharp
private void Menu_Opened(object sender, RoutedEventArgs e)
{
    DittoShell.App.App.MenuOpened(sender, e);
}
```

`App.xaml.cs`：

```csharp
public static void MenuOpened(object sender, RoutedEventArgs e)
    => OnAnyMenuOpened(sender, e);

private static void OnAnyMenuOpened(object sender, RoutedEventArgs e)
{
    if (sender is not ContextMenu menu) return;
    if (!GetCursorPosMenu(out var p)) return;

    var x = p.X;
    var y = p.Y;

    menu.Dispatcher.BeginInvoke(new Action(() =>
    {
        if (PresentationSource.FromVisual(menu) is HwndSource src)
            SetWindowPosMenu(src.Handle, IntPtr.Zero, x, y, 0, 0,
                SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE);
    }), DispatcherPriority.Send);
}
```

**`menuverify` 自动化测试通过**：

```
VERIFY target=(600,400) actual=(600,400) match=True
08:14:12.487 [MainWindowView] Opened cursor=(600,400)
08:14:12.492 [MainWindowView] SetWindowPos ok=True before=(446,417) after=(600,400)
```

**但用户实测仍然是左下。**

### 尝试 8（进行中）：修 `启动.bat` 确保测的是最新版本

发现 `启动.bat` **不杀旧进程**，构建失败后仍启动**旧 exe**。已重写为 4 步（杀进程 → 编译 → 时间戳检查 → 启动），并新增 `tools/check-build.ps1`。

**修复后用户实测：「还是有问题」。**

## 五、建议方向（未验证）

### 方向 A：验证 `WindowChrome` 是否是根因（**最高优先级**）

**实验方法**：

1. 临时注释掉 `MainWindowView.xaml` 里的 `WindowChrome.WindowChrome`
2. 改用 `WindowStyle="None"` + `AllowsTransparency=False`（可能出现无标题栏但可用的窗口）
3. 右键测试菜单位置
4. 如果正常 → 确认 `WindowChrome` 是元凶

**如果确认**：

- 改用 `System.Windows.Shell.WindowChrome` 的替代方案（如自定义标题栏 + `WM_NCHITTEST` 处理）
- 或者参考 `MahApps.Metro` / `ModernWpf` 如何解决 `WindowChrome` + Popup 定位

**参考**：`WindowChrome` 会设置 `HwndSource.CompositionTarget.TransformFromDevice`，并改变 `Visual.TransformToDevice`，可能导致 `PointToScreen` 和 `GetCursorPos` 的坐标系不一致。

### 方向 B：完全不用 `ContextMenu`，改用自定义 `Popup`

```csharp
var popup = new Popup
{
    Placement = PlacementMode.Absolute,
    HorizontalOffset = screenX,
    VerticalOffset = screenY,
    AllowsTransparency = true,
    StaysOpen = false,
    Child = /* 自定义 Border + ItemsControl */
};
popup.IsOpen = true;
```

**优点**：完全可控，不受 `ContextMenu` 内部逻辑影响
**缺点**：需要自己实现菜单项悬停、子菜单、键盘导航、Esc 关闭

### 方向 C：用 `Window` 代替 `ContextMenu`

弹一个无边框、`ShowInTaskbar=false`、`Topmost=true` 的小窗口作为菜单。

**优点**：窗口定位完全可控（`Window.Left/Top`）
**缺点**：需要处理失焦关闭、多窗口管理

### 方向 D：检查 DPI 缩放

```csharp
var dpi = VisualTreeHelper.GetDpi(this);
menu.HorizontalOffset = p.X / dpi.DpiScaleX;
menu.VerticalOffset = p.Y / dpi.DpiScaleY;
```

**未验证**。如果用户系统 DPI 不是 100%，`GetCursorPos` 返回物理像素但 WPF 用 DIP，会有比例偏差。**但从截图看偏移量（-170px）等于菜单宽度，不像是 DPI 问题。**

### 方向 E：检查 `SystemParameters.WorkArea`

多显示器时 `SystemParameters.WorkArea` 只返回**主显示器**的工作区。如果窗口在副显示器，`ContextMenu` 的边界计算可能出错。

```csharp
var screen = System.Windows.Forms.Screen.FromPoint(
    new System.Drawing.Point(p.X, p.Y));
```

## 七、踩过的坑（避免重复）

| 坑 | 教训 |
|---|---|
| `[DllImport("user32.dll")]` 加自定义方法名 | **必须写 `EntryPoint`**，否则运行时抛 `EntryPointNotFoundException`，被 `catch {}` 静默吞掉 |
| `try { ... } catch { }` 包住 P/Invoke | **会隐藏所有错误**。至少在 catch 里写日志 |
| `str.replace()` 做代码修改 | **找不到时静默不报错**。必须用 `assert old in s` 或行号定位 |
| 行号定位后没验证 | 用 `sed -n 'N,Mp'` 打印确认 |
| `EventSetter` 用于隐式 Style | 对 `ContextMenu` **不生效** |
| `RegisterClassHandler` 用于附加事件 | 对 `ContextMenuService.ContextMenuOpeningEvent` **不可靠** |
| `RegisterClassHandler(ContextMenu.LoadedEvent)` | `ContextMenu` 的 `Loaded` **不触发** |
| `ContextMenu.Opening` 事件 | **不存在**。正确的是宿主元素的 `ContextMenuOpening` |
| `启动.bat` 不杀旧进程 | 构建失败仍启动旧 exe，导致「改了没效果」 |
| `.bat` 用 UTF-8 BOM | cmd 把 `﻿@echo` 当命令报错。**用 GBK** |
| `.ps1` 用 UTF-8 无 BOM | PowerShell 5 中文乱码。**用 UTF-8 with BOM 或纯英文** |

## 九、给接手 AI 的建议顺序

1. **先跑 `auditmenus`**，确认当前代码真的移动了菜单窗口（`before` vs `after`）
2. **做方向 A 的对照实验**（去掉 `WindowChrome`），这是最快能定位根因的
3. 如果 `WindowChrome` 确认是元凶，研究 `WindowChrome` 的替代方案（自定义标题栏 + `WM_NCHITTEST`）
4. 如果不想动 `WindowChrome`，用方向 B/C（自定义 `Popup` 或 `Window`）
5. **每改一步都用 `menuverify` 验证实际 HWND 坐标**，不要靠肉眼
