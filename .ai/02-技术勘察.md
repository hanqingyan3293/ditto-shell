实测格式分布（6170 条样本）：

| 格式 | 条数 | 用途 |
|---|---|---|
| `CF_UNICODETEXT` | 5461 | **全文文本**（UTF-16LE 原始字节） |
| `CF_TEXT` | 5432 | ANSI 文本 |

### 其他表

| 表 | 用途 |
|---|---|
| `CopyBuffers(lClipID, lCopyBuffer)` | 复制缓冲区关联 |
| `MainDeletes(clipID, modifiedDate)` | 删除日志（触发器写入） |
| `Types(lID, TypeText)` | 剪辑类型（当前 0 行） |

### 触发器（重要）

```sql
-- 删除 Main 时记录到 MainDeletes
CREATE TRIGGER delete_data_trigger BEFORE DELETE ON Main ...
-- 删除 MainDeletes 时真正清除 Data 和 CopyBuffers
CREATE TRIGGER MainDeletes_delete_data_trigger BEFORE DELETE ON MainDeletes ...
```
⚠️ 含义：**直接从 `Main` 删行不会立即释放空间**，数据在 `MainDeletes` 被清理时才真正删除。这也解释了 830MB 里可能有大量"已删未清"的图片。

### 索引（可直接利用）

`Main_TopLevel`、`Main_TopLevelParentID`、`Main_ClipOrder`、`Main_ClipGroupOrder`、`Main_CRC`、`Main_IsGroup`、`Main_ParentId`、`Main_ShortCut2`、`Main_MoveToGroup`、`Data_ParentId_Format`

→ 列表查询、按组查询、按 CRC 查、按快捷键查**都有现成索引**，无需自建。

## 5. ChaiScript 脚本钩子 ⚠️

来源：`src/DittoChaiScript.h`、`src/ChaiScriptOnCopy.cpp:34-52`

Ditto 支持「复制时执行脚本」。暴露给脚本的能力：

| 函数 | 用途 |
|---|---|
| `GetAsciiString()` / `SetAsciiString(s)` | 读写 ANSI 文本 |
| `GetUnicodeString()` / `SetUnicodeString(s)` | 读写 Unicode 文本 |
| `GetClipMD5(fmt)` / `GetClipSize(fmt)` | 查内容指纹和大小 |
| `GetActiveApp()` / `GetActiveAppTitle()` | **拿来源进程名和窗口标题** |
| `SetParentId(id)` | **直接改分组归属** |
| `SetMakeTopSticky()` / `SetMakeLastSticky()` / `SetReplaceTopSticky()` | 置顶操作 |
| `FormatExists(fmt)` / `RemoveFormat(fmt)` | 查/删某个剪贴板格式 |
| `AsciiTextMatchesRegex(r)` / `AsciiTextReplaceRegex(r, s)` | 正则匹配与替换 |
| `DescriptionMatchesRegex(r)` / `DescriptionReplaceRegex(r, s)` | 描述字段的正则操作 |

⚠️ **限制**：脚本引擎没有网络能力、没有文件读写，不能直接调 AI API。
✅ **价值**：`GetActiveApp()` 是 Ditto 唯一能拿到"来源应用"的官方通道；`SetParentId()` 是官方改分组通道。

## 7. 验证结果（2026-11-15 实测）

### V1 · 全文搜索方案 ✅ 结论：**放弃 FTS5，直接用 LIKE**

**起因**：担心 FTS5 中文分词效果差（风险 R2）。

**实测数据**（真实库 6,179 条 / 755,004 字符）：

| 查询方式 | 磁盘库耗时 | 内存库耗时 |
|---|---|---|
| `LIKE '%github%'` | 7.1 ms | 2.2 ms |
| `LIKE '%gh auth%'` | 5.7 ms | 2.3 ms |
| `LIKE '%不做云同步%'` | 6.8 ms | 2.1 ms |
| 完整查询（LIKE + 排序 + LIMIT 50） | 9.1 ms | — |
| 首页加载（最近 50 条） | 10.8 ms | — |
| FTS5 trigram 建索引 | — | 281 ms |
| FTS5 trigram 查询 | — | 0.1–0.3 ms |

**关键发现：FTS5 的 `trigram` 分词器对 2 字中文词完全失效**

| 查询词 | trigram 命中 | LIKE 命中 |
|---|---|---|
| `配装` | **0** | 1 ✅ |
| `枪械` | **0** | 1 ✅ |
| `枪械配装`（4 字） | 1 | 1 |

原因：trigram 按 3 字符滑窗切分，2 个汉字凑不成一个 trigram。而中文里的常用词大量是 2 字（配装、枪械、密码、搜索、分组、密钥…）。

**结论**：
- 放弃 FTS5，搜索用 `LIKE '%关键词%'` 全表扫描
- 实测 6 千条 6–11ms，估算 5 万条约 50–60ms（目标 <150ms，安全）
- **收益**：省掉 20–30MB 索引文件、省掉索引同步逻辑、中文零配置、100% 召回
- 若未来超 50 万条再考虑 FTS5 + jieba 预分词

### V2 · WPF 在 Win10 + 125% DPI 的视觉可行性 ✅ 结论：**可行，观感达 mockup 的 85–90%**

**环境实测**：Windows 10 Pro / Build 19045（22H2）/ 系统缩放 125%（DPI 1.25）

**验证程序**：`tools/verify-v2/`（WPF 最小窗口，圆角 12 + 自绘阴影 + 浅色列表，渲染到 `v2.png`）

| 项 | 结果 |
|---|---|
| 圆角（12px） | ✅ 正常，无锯齿 |
| 自绘阴影（DropShadowEffect） | ⚠️ 偏淡，需加大 BlurRadius/Opacity 或叠加两层 |
| 125% DPI 文字清晰度 | ✅ 清晰，无模糊（渲染出 588×750 实际像素） |
| 中英混排 / 等宽字体 | ✅ 正常 |
| 彩色圆点 / 渐变缩略图 / 标签 | ✅ 正常 |
| Mica 背景 | ❌ Win10 不支持（用纯白 + 自绘阴影替代，观感可接受） |
| 整体观感 vs HTML mockup | 85–90%，差距在**行高与字号比例、间距精细度、阴影强度** —— 属调优问题，非平台天花 |

**结论**：WPF 方案成立。进入实现阶段时需要专门调这三项：行高（46 DIP → 42）、阴影参数、垂直对齐基线。
