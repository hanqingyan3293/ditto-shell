# 决策记录（ADR）

> 每做一个不可逆或影响面大的选择，就在这记一条。格式：编号 / 日期 / 结论 / 理由 / 替代方案 / 何时需要重审。

---

## ADR-001 · 不 fork Ditto 重编译，走独立外壳

- **日期**：2026-11-15
- **结论**：Ditto 本体保持原样，新界面做成独立进程。
- **理由**：
  1. Ditto 是 178 个 cpp 的 MFC 工程，编译环境（VS + MFC + Windows SDK）对非程序员门槛过高；
  2. 界面控件是自绘的，改外观≈重写；
  3. 每次上游升级都要重新合并；
  4. 外壳方案下 Ditto 坏不了，最坏情况是外壳不能用。
- **替代方案**：fork 后改 `QPasteWnd`；写 Addin DLL（保留为未来增强）。
- **重审条件**：外壳方案撞到无法绕过的墙（例如必须改捕获逻辑）。

## ADR-002 · 新界面技术栈：WPF (.NET 8) 首选

- **日期**：2026-11-15
- **结论**：首选 WPF + .NET 8 单文件发布；Tauri 作为备选。
- **理由**：
  1. 冷启动约 200ms（剪贴板面板必须"按下就出来"）；
  2. 常驻内存约 40MB，与 Ditto 本身同量级；
  3. Win11 的亚克力/Mica 背景可用 `DwmSetWindowAttribute` 直接获得，不需要 WebView；
  4. 不依赖 WebView2 版本，不引入 Rust 工具链；
  5. AI 生成 C#/XAML 的返工率低于 QML/Qt。
- **替代方案**：Tauri 2 + React（观感上限更高，但常驻约 100MB、冷启动约 600ms）。
- **重审条件**：用户对视觉效果要求高于资源占用时，切 Tauri。

## ADR-003 · 与 Ditto 的通信只用「命令行 + 窗口消息」

- **日期**：2026-11-15
- **结论**：
  - 粘贴：`Ditto.exe /paste:<ID>`
  - 刷新/开关/其它：`SendMessage(hwnd, WM_USER+n, ...)`
- **理由**：两者都在源码里验证过，是 Ditto 自己内部用的通道，不是逆向出来的私有协议。粘贴由 Ditto 完成，杜绝 HTML/DIB/HDROP 格式还原的坑。
- **替代方案**：外壳自己 `SetClipboardData` + `SendInput`（格式坑太多）。
- **重审条件**：命令行启动开销（约 30–80ms）影响到交互手感时，改用消息直连。

## ADR-004 · 数据库只读打开，索引和标签放旁路库

- **日期**：2026-11-15
- **结论**：
  - `Ditto.db` 以 `mode=ro` 打开；
  - 全文索引、标签、AI 向量、来源应用 → 全部存 `data/sidecar.db`。
- **理由**：`journal_mode=delete`（非 WAL），外部写会与 Ditto 抢锁；旁路库坏了可重建。
- **重审条件**：进入"改分组"阶段时，为写操作单独开一条受控通道（见 ADR-007 待补）。

## ADR-005 · 全文搜索从 `Data.CF_UNICODETEXT` 取，不用 `mText`

- **日期**：2026-11-15
- **结论**：索引数据源是 `Data` 表里的全文，`Main.mText` 只用于列表预览。
- **理由**：实测 `mText` 最长 900 字符，用它做搜索会漏掉长文本的后半段。
- **代价**：首次建索引需读 14543 行 BLOB，预计 1 分钟内完成；索引文件约 10MB。
- **重审条件**：数据库增长到 10 万条以上时，改为增量建索引。

## ADR-006 · AI 分档，默认关闭

- **日期**：2026-11-15
- **结论**：
  - 档位 0（默认）：无 AI，纯全文 + 规则
  - 档位 1：本地 embedding（bge-small-zh 量化，约 25MB 模型 + 约 10MB 索引），空闲可卸载
  - 档位 2：云端 API，按按钮触发，不常驻
  - 明确放弃：本地大模型常驻（1.5–2GB）
- **理由**：用户明确要求低存储低占用；6170 条数据量下，本地 embedding 的收益/成本比最好。
- **重审条件**：数据量级变化，或本地小模型（<300MB）效果足够好。

## ADR-007 · 写库边界：受控写入 3 个字段

- **日期**：2026-11-15
- **结论**：允许外壳写 `Ditto.db`，但**只允许改 3 个字段**：
  1. `Main.lParentID`（分组归属）
  2. `Main.stickyClipOrder` / `stickyGroupOrder`（置顶）
  3. `Main.lDontAutoDelete`（保留标记）
- **强制流程**：写前备份到 `backup/` → 单事务 → 写完发 `WM_REFRESH_VIEW` 让 Ditto 重读 → 失败自动回滚。
- **理由**：① 旧界面能同步看到整理结果，避免两套界面割裂；② 只改整数字段，出错最坏是"某条跑错组"，可 5 分钟恢复。
- **禁止**：改表结构、改 PRAGMA、删 `Main` 行、碰 `Data` 表。
- **重审条件**：Ditto 大版本升级后字段语义变动（概率低，这 3 个字段 10 年未变）。

## ADR-008 · 许可证：GPL v3，开发期间不发布

- **日期**：2026-11-15
- **结论**：项目以 **GPL v3** 发布；开发阶段完全私有，达到"完整可发布"状态后才公开。
- **理由（GPL 其实更安全）**：
  - 进程边界读写 + 消息通信本就不构成衍生，MIT 也合法；
  - 但 GPL v3 让我们**法律上完全无顾虑**：未来若想做 Ditto Addin（进程内 DLL）、或直接分发含 Ditto 的安装包，都不会有许可证冲突；
  - 代价是别人用我们的代码也必须开源 —— 对自用 + 开源的项目无实质损失。
- **注意**：GPL v3 要求分发时提供完整对应源码，所以发布包必须附源码或指向仓库。

## ADR-009 · 发布形态：绿色便携 zip 起步

- **日期**：2026-11-15
- **结论**：首发为解压即用的 zip；稳定后再考虑 winget/scoop；安装包（需代码签名证书）暂不做。
- **理由**：与用户当前的便携版 Ditto 一致，零安装成本，不需要买签名证书。

## ADR-010 · 旧界面：完整隐藏 + 两条复活通道

- **日期**：2026-11-15
- **结论**：
  - 启动时不显示 Ditto 主窗口（用 `/close` 或让它后台运行）；
  - 复活方式：① 托盘右键菜单「经典界面」；② 设置面板里的开关。
- **理由**：既满足"完整隐藏"的清爽感，又保留兜底能力。

## ADR-011 · 目标用户：已在用 Ditto 的人

- **日期**：2026-11-15
- **结论**：不做"从零安装 Ditto"的引导。外壳检测 Ditto 是否安装、版本是否兼容，不满足则给出明确提示。
- **理由**：不做小白引导 = 不需要内置分发 Ditto（避开 GPL 分发义务和体积膨胀）。

## ADR-012 · AI 隐私边界

- **日期**：2026-11-15
- **结论**：
  1. **只上传用户主动选中的条目**，绝不后台批量上传；
  2. **指定分组永不外发**（用户可设黑名单，默认包含"凭据/密码"类）；
  3. 发送前过一次本地敏感信息检测（token/密码/身份证 → 打码）；
  4. API Key 存 Windows 凭据管理器，不明文落盘。
- **理由**：实测数据库里已存在明文 GitHub Token（ID 9783），这是真实风险不是假设。

## ADR-013 · 规模策略：FTS5 直上，不做增量复杂度

- **日期**：2026-11-15
- **结论**：目标 1–2 万条、上限 5 万条。全文索引用 SQLite FTS5 一次性建 + 增量追加，不引入外部搜索引擎。
- **理由**：5 万条 × 平均数百字 ≈ 几十 MB 索引，FTS5 毫秒级返回，无需更复杂方案。

## ADR-014 · 三界面架构：快速面板 / 主界面 / 原界面

- **日期**：2026-11-15
- **结论**：产品由三块界面组成，职责严格不重叠。

| 界面 | 尺寸 | 触发 | 平时占比 | 只做这些 | 绝对不做 |
|---|---|---|---|---|---|
| ① 快速面板 | 428×556 悬浮 | `Ctrl+``  | ~90% | 搜索、选择、粘贴、数字键 1-9 直粘 | 不显示分组、不做设置、不做批量 |
| ② 主界面 | 780×642 窗口 | `Ctrl+Shift+`` 或面板里的「管理历史」 | ~10% | 分组、标签、AI 检索、预览（点 ⋯ 展开三栏）、导入导出、设置 | 不抢快速粘贴的快捷键 |
| ③ Ditto 原界面 | 原样 | 托盘右键「经典界面」/ 设置开关 | ≈0% | 兜底 | 默认完全隐藏，不主动弹出 |

- **视觉语言**（对齐 snow-shot / Ant Design）：
  - 浅色平铺，**不用卡片、不用深色块**，靠留白 + 字重 + 极淡分割线区分
  - 主色 `#1677FF`（交互）、品牌紫 `#722ED1`（logo）
  - 选中态 `#E6F4FF` 底 + `#1677FF` 字，圆角 6px
  - 搜索框灰底 `#F5F5F5` 无边框
  - 字号：正文 13px / 元信息 11.5px
- **原型文件**：`docs/mockups/E-quick.html`（快速面板）、`A2-light.html`（主界面）、`A2-light-expand.html`（展开态）、`flows.html`（三界面关系）
- **重审条件**：用户使用一周后觉得快速面板太窄或主界面太重。

## ADR-015 · 热键必须接管 Ditto 原键位

- **日期**：2026-11-15
- **结论**：外壳的快速面板占用 `Ctrl+``（Ditto 当前使用的键），因此**必须在 Ditto 里释放该键**。
- **做法**：
  1. 首次启动时检测 Ditto 是否占用了 `Ctrl+``；
  2. 若占用，弹出一张中文引导卡，带「我来改」按钮（调用 Ditto 设置界面）或手动步骤截图；
  3. 改完后外壳才启用热键。
- **理由**：用户肌肉记忆在 `Ctrl+``，不改这个键是最小惊讶原则。
- **风险**：Ditto 设置界面是英文/中文混合，用户可能改错 → 提供"还原"入口。

## ADR-016 · Ditto 原生设置全量迁移到外壳（分三级）

- **日期**：2026-11-15
- **结论**：`Ditto.Settings` 是 **UTF-16LE 的 INI 文本**（实测可读可写），共 **77 个设置键**。外壳提供设置界面，按三级呈现：

| 级别 | 数量 | 内容 | 呈现方式 |
|---|---|---|---|
| **P0 常用** | 约 18 | 保留策略（MaxEntries / 过期清理 / 单条大小）、快捷键、语言、主题、搜索模式、纯文本粘贴、来源过滤 | 设置页第一屏，平铺可见 |
| **P1 高级** | 约 25 | 粘贴延迟、按键延迟、管理员粘贴、MD5 校验、大文件上限、空闲清理、提示超时 | 折叠区「高级」，默认收起 |
| **P2 不迁** | 约 34 | 内部调试键（`FunnyTickCountAdjustment` `DragId` `DiffApp` 等）、多机同步（`sendclient_*`，用户明确不做） | 不显示；另给「打开 Ditto 原设置」入口 |

- **写回规则**：
  1. 改前备份 `Ditto.Settings` 到 `backup/`；
  2. 只改目标键，其余行原样保留（按行编辑，不重写整个文件）；
  3. 写完提示「部分设置需重启 Ditto 生效」，并提供一键重启。
- **理由**：用户不懂英文，Ditto 的选项树对他来说等于黑盒；把 77 个键翻译成中文表单，价值极高。

## ADR-017 · 搜索用斜杠命令面板，不要求用户记语法

- **日期**：2026-11-15
- **结论**：
  - 搜索框内输入 `/` 弹出命令面板（对齐 Codex 的命令面板形态）；
  - 面板列出全部筛选器，每项带「图标 + 中文名 + 语法别名 + 示例值 + ›」；
  - `↑↓` 选择、`Enter` 展开二级（如分组列表、类型列表）、`Esc` 关闭；
  - 二级选择后自动把语法写入搜索框（如 `g:M4A1`），用户可以继续打字；
  - **不改语法本身**，只是把它藏在面板后面 —— 熟练用户仍可直接手打 `g:M4A1`。
- **理由**：用户明确反馈「前缀太难记」。面板解决发现性问题，语法解决效率问题，两者共存。

## ADR-018 · 图片：存储沿用 Ditto，显示加内存缓存

- **日期**：2026-11-15
- **结论**：
  - **存储不动**：继续用 Ditto 的 `CF_DIB` 原始位图，不转码、不迁移、不另存；
  - **显示时**：解码 → 缩放到显示尺寸 → 放入**内存 LRU 缓存**（约 100 张，估 20–30MB），不落盘；
  - 右键提供「复制原图」「另存为 PNG」，文件类条目额外提供「打开所在位置」。
- **理由**：用户选择"采用原 Ditto 方案"，即不改变数据形态；落盘缩略图缓存会引入额外目录和一致性问题，内存缓存可随时丢弃。
- **代价**：冷启动首次滚动时，大图（8MB+）转换约 50–100ms/张，有明显迟滞 → 用后台预取缓解。

## ADR-019 · 分组支持多层嵌套与完整增删改

- **日期**：2026-11-15
- **事实更正**：用户现有的 35 个组**已是一层嵌套**（5 个顶层 + 30 个挂在同一父组下）。Ditto 的 `CGroupTree::FillTree` 是递归的，数据模型（`lParentID`）支持任意深度。
- **结论**：分组浮层做成树形，支持：
  - 新建 / 重命名 / 删除（删除时组内条目回到「未归类」，不删内容）
  - 在任意层「新建子组」
  - 拖动改变父级
  - 不限层数，但第 4 层起提示「建议不超过 3 层」
- **写库**：新建组 = `INSERT INTO Main (bIsGroup=1, lParentID=父ID, clipOrder=同层最大+1)`，走 ADR-007 的受控写入流程。

## ADR-020 · 平台支持 Win10 + Win11

- **日期**：2026-11-15
- **结论**：最低 Windows 10 1809（含）。背景效果分两档：

| 系统 | 窗口背景 | 圆角 | 阴影 |
|---|---|---|---|
| Win11 | Mica / Acrylic（`DwmSetWindowAttribute`） | 系统原生 | 系统原生 |
| Win10 | 纯色 + 轻微透明（`SetWindowCompositionAttribute` 的 `ACCENT_ENABLE_BLURBEHIND`） | **自绘**（Region + 圆角 clip） | **自绘**（DWM 不给 Win10 圆角阴影） |

- **代价**：Win10 分支多约 200 行窗口样式代码，视觉效果略逊（模糊更"脏"，没有 Mica 的壁纸取色）。
- **理由**：用户明确要求支持 Win10；且 Win10 仍有大量存量用户，开源出去不能只服务 Win11。

## ADR-021 · 中英双语，从第一天就做 i18n 结构

- **日期**：2026-11-15
- **结论**：
  - 所有界面文案抽到 `src/.../Resources/Strings.zh-CN.json` 和 `Strings.en.json`
  - 代码中不出现硬编码中文（用 `L.T("key")`）

## ADR-022 · AI：用户自填 Key，OpenAI 兼容协议，模型名可配

- **日期**：2026-11-15
- **结论**：
  - 使用 **OpenAI 兼容的 `/chat/completions` 接口**，`base_url` / `api_key` / `model` 三项全部由用户填写
  - 默认预置 DeepSeek：`base_url = https://api.deepseek.com`，`model = deepseek-flash`
  - API Key 存 Windows 凭据管理器（`Credential Manager`），配置文件里只留引用
  - 设置页提供「测试连接」按钮，返回模型名 + 延迟 + 可用性
- **⚠️ 模型名核实结果**（查官方文档）：
  - 2026-09-10 起 **`deepseek-flash`** = DeepSeek-V4.1-Flash（1M 上下文 / 384K 输出 / **支持图片输入**）
  - `deepseek-v4-pro` = V4-Pro（纯文本）
  - `deepseek-v4-flash` 是**已退休别名**，仍可调用但会路由到 V4.1-Flash
  - 用户说的「dsv4f」应写 **`deepseek-flash`**，而不是旧别名
- **额外机会**：`deepseek-flash` 支持图片输入 → 剪贴板里的截图可以直接让 AI 理解（"这张图是什么"），作为 P2 功能预留。

## ADR-025 · 外壳菜单统一优先向右展开

- **日期**：2026-11-17
- **问题**：本机 Windows 的 MenuDropAlignment（菜单右边缘对齐）为 1；WPF 据此把一级和多级菜单优先放到左侧。普通窗口、WindowChrome（自定义窗口边框）及透明窗口对照实验均复现，因此窗口边框不是此问题的根因。
- **决定**：只在外壳进程内将 .NET 8 WPF 已核实的 SystemParameters._menuDropAlignment 私有缓存设为 false。先读取公开属性完成缓存初始化；订阅 StaticPropertyChanged（系统参数变更通知），缓存重读时同步重新应用。保留 WPF 菜单、键盘导航及屏幕边缘避让。
- **清理**：移除菜单打开后调用 SetWindowPos（强制移动窗口）的补丁，以及 App.xaml 中尝试禁用默认编辑菜单的样式。各页面已有 MenuOpened 通知只用于日志。
- **边界**：不修改 Windows 注册表、不调用系统参数设置接口、不修改 Ditto 本体或数据库。共享此定位缓存的外壳弹出层也会采用相同默认方向。
- **兼容性**：私有缓存不是公开承诺的接口。初始化检查字段存在、类型和可写性，失败时记录日志并保留系统行为。升级 WPF 后必须执行 tools/verify-menus.ps1；已核对 .NET 8.0.0 和 8.0.28 官方源码。
- **验证**：双屏（含副屏负坐标）、普通/自定义边框/透明窗口、三级菜单、重复打开、右键菜单点击和键盘导航、三种编辑框临时菜单、屏幕右边缘避让；修复版 106 通过/0 失败，跳过修复的对照版 61 通过/45 失败。额外两次调用已核实的 SystemParameters.InvalidateCache(int) 菜单缓存失效路径，未手动重跑修复，通知处理器仍同步保持 false。系统参数开始/结束均为 1。编辑菜单命令只在一次性测试控件内拦截，不写剪贴板；测试入口在配置、依赖服务、数据库、互斥和热键初始化之前运行。
- **备份**：backup/menu-ui-20261117-093624，含修改前源码、文档和 Debug 外壳程序；回退脚本为 tools/menu-fix-backup.ps1。不包含 Ditto.db。
